# @leadshelf/prisma-client

Пустой пакет-обёртка: его `generated/` пишет `prisma generate` (схема —
`packages/db/prisma/schema.prisma`, `output` указывает сюда). В репозитории
генерат не лежит, поэтому после клона нужен один раз

```
pnpm install && pnpm db:generate
```

иначе typecheck и тесты упадут на ненайденном модуле.

## Зачем отдельный пакет, а не `packages/db/generated`

Две причины, обе про прод-образы.

1. **Чистка воркера штатным `pnpm prune --prod`.** Пока генерат лежал по
   умолчанию внутри `node_modules`, prune сносил modules-каталог целиком и
   уносил клиент с собой, а вернуть его было нечем: prisma CLI — dev-зависимость.
   Здесь генерат вне `node_modules`, prune до него не дотягивается.
2. **`serverExternalPackages` у Next.** Клиент грузит нативный движок
   (`libquery_engine-*.so.node`) и читает рядом `schema.prisma`, поэтому его
   нельзя бандлить — он должен остаться внешним. Имя в этом списке обязано быть
   пакетом, который Next НЕ транспилирует, а `@leadshelf/db` транспилируется:
   это TypeScript-исходники. Отсюда отдельное имя.

Генерат самодостаточен: внутри лежит своя копия рантайма, и `@prisma/client`
в рантайме не нужен — он остался только dev-зависимостью `@leadshelf/db`,
нужной самому генератору.

## Перечисления — только как типы

Генерат — CommonJS, и перечисления он объявляет цепочкой
(`exports.TaskStatus = exports.$Enums.TaskStatus = {...}`), которую
детектор именованных экспортов Node не разбирает. Поэтому из ESM

```ts
import { TaskStatus } from "@leadshelf/prisma-client"  // undefined в рантайме
```

молча даёт `undefined`, хотя типы проверку проходят. В репозитории
перечисления и так импортируются только как типы (`import type`), значения
живут в `packages/core`. Если значение всё-таки понадобится — брать через
default-импорт и деструктуризацию, а не именованным импортом.
