# Демо-стенд: запустить LeadShelf и показать клиенту

Стенд — это весь продукт с демо-данными, поднятый из этого репозитория одной
командой. Он нужен, чтобы показать LeadShelf, пока у клиента нет своего
сервера, и чтобы не зависеть от того, жив ли сейчас какой-то конкретный хост.

## Показать на ноутбуке

```bash
scripts/demo.sh up
```

Открыть `http://localhost:8080`. Вход: организация `demo`, почта
`admin@leadshelf.com`, пароль `demo1234`.

Первый запуск собирает образы — это 15–25 минут (ставятся зависимости и
собирается Next.js). Второй и дальше — около минуты. Адрес намеренно
`localhost`: сессионная кука помечена `Secure`, браузеры считают `localhost`
защищённым адресом и куку принимают, а по адресу в локальной сети — уже нет,
поэтому стенд слушает только loopback.

## Дать клиенту ссылку

Нужна машина с публичным IP и домен, A-запись которого уже указывает на неё.

```bash
scripts/demo.sh up --domain demo.example.com
```

Caddy сам возьмёт сертификат Let's Encrypt. Перед стендом стоит пароль
(basic auth) — скрипт печатает пару логин/пароль после запуска и генерирует её
заново на каждый такой запуск. Это не перестраховка: демо-пароль тенанта лежит
в открытом репозитории, и без двери стенд за неделю найдут поисковые боты.

Машине нужны Docker, 4 ГБ памяти (8 ГБ — если поднимать с фоновыми сервисами)
и ~15 ГБ диска.

**Не на dev-боксе Contabo.** Там 80 и 443 держит catch-all nginx BudgetPro:
пустить туда ещё один домен можно только правкой чужого прод-конфига, которую
следующий релиз BudgetPro затрёт, и домен начнёт молча отдавать BudgetPro.
Плюс общий `CLAUDE.md` запрещает сборку образов на этом хосте. Для публичной
ссылки берётся отдельная машина.

## Команды

| Команда | Что делает |
|---|---|
| `scripts/demo.sh up` | поднять локально |
| `scripts/demo.sh up --domain <host>` | поднять публично, HTTPS + пароль на входе |
| `scripts/demo.sh up --port 9000` | другой локальный порт |
| `scripts/demo.sh up --no-workers` | без фоновых сервисов: сборка вдвое короче |
| `scripts/demo.sh status` | что запущено |
| `scripts/demo.sh logs [сервис]` | логи вживую |
| `scripts/demo.sh down` | остановить, данные оставить |
| `scripts/demo.sh reset` | остановить и стереть демо-данные |

## Что показывает стенд

Демо-тенант «LeadShelf Demo» из `packages/db/prisma/seed-demo.ts`: каталог
товаров с размерами упаковки, оборудование и полки, планограммы, маршруты
агентов, визиты с фото-пруфами и аналитика выкладки. Пять пользователей с
разными ролями — администратор, категорийный менеджер, мерчендайзер,
супервайзер, аналитик, — пароль у всех `demo1234`.

Сид идемпотентен: повторный `up` ничего не дублирует.

## Чем стенд отличается от клиентского прода

| | стенд | клиентский прод |
|---|---|---|
| профиль | `LEADSHELF_RUNTIME_PROFILE=demo` | `client`, демо-копии и синтетических картинок нет |
| данные | сид из репозитория | данные клиента |
| распознавание фото | `VISION_PROVIDER=stub`, без внешнего ключа | Gemini, ключ в `.env.production` |
| хранилище | MinIO в контейнере | внешний S3/R2 с versioning и retention |
| бэкапы | нет | restic вне машины + проверенный restore drill |
| релиз | `git pull` и `up` | расписка релиза, exact SHA, бэкап до миграций |

Стенд намеренно не проходит эти гейты: он для показа, не для данных клиента.

### Про объектное хранилище

Официальные образы MinIO больше не отдаются анонимно: и `minio/minio`, и
`quay.io/minio/minio` отвечают `pull access denied`. Это задевает не только
стенд — цифровой пин в `deploy/docker-compose.prod.yml` на чистой машине
тоже не скачается, то есть поднять прод с нуля этим файлом сейчас нельзя.
Работающие прод-хосты не затронуты: образ у них уже локальный.

Стенд из-за этого стоит на последнем публичном зеркале Bitnami, пришпиленном
по digest. Образ заморожен и секурити-фиксов не получает, поэтому для данных
клиента он не годится — и не должен: `deploy/SERVER_SETUP.md` и без того
требует внешний S3/R2 с versioning и retention как условие запуска. Когда
дойдёт до первого клиента, объектное хранилище выбирается там, а не здесь.

## Клиент сказал «да»

Разворачивать у клиента надо не стендом, а прод-путём — он другой по
устройству, а не по настройке:

1. `deploy/SERVER_SETUP.md` — сервер, раскладка `/opt/leadshelf/prod`,
   `.env.production`, разделение dev и prod.
2. `deploy/SERVER_SETUP.md` шаг 5 и `deploy/OPERATIONS_RUNBOOK.md` — бэкапы и
   restore drill **до** загрузки боевых данных.
3. `deploy/docker-compose.prod.yml` — тот же набор сервисов, но профиль
   `client`, внешний S3 и релизные гейты.
4. `docs/DELIVERY-ARCHITECTURE.md` — как изменения доезжают до клиента.

## Проверка

`.github/workflows/demo-stand.yml` на каждый PR поднимает стенд на чистой
машине, логинится демо-пользователем и убеждается, что каталог отдаёт товары
из сида. Если стенд перестанет подниматься одной командой, это видно в CI, а
не за полчаса до встречи с клиентом.
