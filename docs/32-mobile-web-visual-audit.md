# LeadShelf mobile ↔ web visual audit

Обновлено: 2026-07-10. Проверяемый commit: `c2427e1`.

## Объём и достоверность

Подтверждено визуально:

- web execution surfaces (`Задачи`, `Поле`, `Заказы`) при 390, 768 и
  1440 px по девяти актуальным Playwright screenshots;
- отсутствие горизонтального overflow на этих ширинах;
- семантические роли цветов, плотность, порядок действий и responsive
  композиция.

Подтверждено по mobile-коду и тестам, но ещё не полностью на устройстве:

- пять нижних вкладок, SyncBar, indigo hero, active-visit card;
- offline order composer, локальная очередь, task badge, skeleton первого
  sync и check-in/check-out guards;
- использование одних и тех же az/ru status labels на маршруте, в визите
  и в полном списке задач.

Нативный visual smoke текущего commit выполнен **частично** локально. Arm64
release APK собран и установлен на Android 15 / API 35 AVD; подтверждены
холодный старт без native crash, login screen, az/ru switch, заполненная demo
organization и успешный вход `M-001`. После входа подтверждены пять tabs,
indigo hero, SyncBar и честный empty route state на production API.

Для полного воспроизводимого сценария поднят локальный demo API, выполнен seed
и установлена отдельная smoke-сборка с `10.0.2.2:3100`. Автоматическое
управление было остановлено лимитом подтверждений среды до повторного входа,
поэтому check-in, composer, queue и checkout ниже не выдаются за визуально
подтверждённые device-факты.

## Что уже согласовано хорошо

### 1. Один семантический язык, разные рабочие оболочки

Mobile использует indigo для текущего раздела и главного действия, green
для активного/успешного состояния, amber для ожидания и red для
destructive/error. Web использует те же роли. Значения primary немного
различаются (`#6366F1` mobile и indigo-600 web), но воспринимаются как одна
система и не требуют общего runtime-пакета.

Пять нижних вкладок mobile и sidebar/компактная top navigation web не нужно
делать одинаковыми. Это корректное различие ролей: агенту важны маршрут и
активный визит большим пальцем, офису — параллельный доступ к каталогу,
планограммам, review и аналитике.

### 2. Сквозной execution story читается на обеих поверхностях

На mobile рабочая последовательность начинается с магазина и визита; на
web — с маршрута, review или заказа. При этом общие сущности и термины
совпадают: точка, маршрут, визит, задача, заказ, pending/conflict/rejected.
Web Field Force уже показывает задачи и заказы выбранной точки, а orders
объясняет, что синхронизированный mobile order появится в офисе.

### 3. Responsive web не является уменьшенной desktop-таблицей

На 390 px задачи переходят в карточку, orders — в вертикальные summary и
empty-state, Field Force — в последовательность выбранного маршрута и
списка. Критические действия остаются читаемыми, а primary indigo не
конкурирует с destructive red.

## Критика и рекомендации

### VA-01 — P0: закрыть native acceptance текущего commit

Ни один code review или web screenshot не подтверждает keyboard avoiding,
safe areas, haptic timing, реальную высоту tab bar, 40+ SKU scrolling и
camera-to-task transitions. Definition of Done остаётся прежним:

1. release/preview APK из текущего SHA;
2. установка на Android API 31+ device/emulator;
3. Maestro `login → route → check-in → order → checkout`;
4. screenshots маршрута, composer, локальной очереди и завершённого визита.

Пункты 1–2 закрыты локальной сборкой. До screenshots и полного flow MW-03 и
фактическая Android-часть MW-14 остаются частичными.

### VA-02 — P1: orders на телефоне должен начинаться с результата

На web 390 px блок операционной телеметрии занимает значительную часть
первого экрана до списка заказов. Для офисного пользователя основной
вопрос — появился ли заказ и требует ли он действия. При появлении данных
рекомендуемый порядок:

1. compact totals + exception filter;
2. order cards;
3. свернутый/вторичный sync health block.

На desktop текущая observability panel уместна и может оставаться выше
таблицы, потому что ширина не вытесняет результат за fold.

### VA-03 — P1: уменьшить длину Field Force на 390 px

Phone composition функциональна, но одновременно показывает module nav,
детали выбранного маршрута, фильтры, три route actions и длинный список
карточек. Это создаёт больше решений, чем нужно для быстрого контроля.
Следующий срез должен оставить выбранный маршрут и его alerts открытыми,
а завершённые/отменённые маршруты сгруппировать или сворачивать. Primary
action `Новый маршрут` не должен визуально конкурировать с выбранным
маршрутом после входа по deep link.

### VA-04 — P1: сохранить единые локализованные статусы задач

В route/visit preview использовались сырые значения enum, тогда как список
mobile tasks и web показывают локализованные labels. В рамках аудита это
исправлено через уже существующие `status_*` ключи; новые строки и изменения
протокола не понадобились.

### VA-05 — P2: не обещать цену до появления офлайн-источника цены

Mobile composer честно показывает виды товаров и количество, но не сумму.
Web order после sync показывает серверную коммерческую сумму. Добавлять
псевдоцену из planogram bundle нельзя: текущий локальный catalog projection
цены не содержит, а контракт order.create передаёт только productId и
quantity. До отдельного согласования offline price source это различие
нужно сохранять и объяснять как lifecycle, а не маскировать нулями.

### VA-06 — P2: проверить визуальную иерархию активного визита на device

В mobile одновременно доступны завершение визита на вкладке `Маршрут` и
полный набор действий на вкладке `Визит`. Это соответствует образцу
владельца и ускоряет checkout, поэтому менять до device-test не следует.
Во время native audit нужно проверить только риск случайного destructive
tap рядом с нижними вкладками и различимость disabled local-visit state.

## Следующий приоритет

1. Разблокировать VA-01 без изменения frozen protocol.
2. После нативных screenshots устранить только подтверждённые mobile
   дефекты, не перепроектируя утверждённый owner reference.
3. Затем выполнить VA-02 и VA-03 как отдельный responsive web slice с теми
   же 390/768/1440 regression screenshots.
