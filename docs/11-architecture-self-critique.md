# Самокритика по архитектуре (2026-07-02)

Критика архитектуры из docs/02 + моих bootstrap-решений. Схемные баги
разобраны в docs/10 и исправлены; здесь — уровень системы. Отсортировано
по опасности.

## 1. Tenant isolation нигде не enforce'ится (самое опасное)

Схема даёт `organizationId` везде, но НИ ОДИН слой не гарантирует, что запрос
не утечёт в чужой тенант. В MTM скоупинг делался вручную в каждом route
handler — это классический источник багов, и я молча унаследовал этот подход.
Codex-ревью предлагает композитные tenant-FK; я решил иначе (см.
`packages/db/prisma/MIGRATION_NOTES.md` п.5), но решение должно быть
РЕАЛИЗОВАНО, а не задекларировано:

- **Действие:** scoped Prisma client в `packages/db` (client extension,
  автоматически инжектящий `organizationId` в where/create) — единственный
  разрешённый способ доступа к БД из route handlers. Голый клиент — только
  worker/миграции.
- **Действие:** интеграционный тест «тенант A не видит данные тенанта B»
  на каждый корневой агрегат.
- RLS — кандидат на v2, не сейчас (усложняет Prisma-флоу).

## 2. Backend внутри Next.js — мы повторяем грех MTM

MTM страдал от того, что бизнес-логика жила в route handlers веб-приложения.
Мой план «портировать 10k строк API в Next.js route handlers» воспроизводит
ту же связанность: деплой админки = деплой мобильного API, невозможность
масштабировать их раздельно. Осознанный trade-off для 1-2 разработчиков
(скорость > чистота), но он держится ТОЛЬКО на дисциплине:

- **Правило:** route handler = парсинг (zod из api-contracts) → вызов
  функции из packages/core или сервиса → сериализация. Ноль бизнес-логики
  в handlers. Проверять на code review.
- **Ловушка:** соблазн мешать server actions и route handlers для одного и
  того же — мобильному нужны route handlers, вебу удобнее actions. Решить:
  всё, что нужно мобильному, — только route handlers.

## 3. API-версионирование для offline-клиентов не решено

Полевые телефоны обновляются неделями. Сломанный контракт = сломанное поле.
В скелете нет ни `/api/v1`-стратегии, ни versioning в api-contracts, ни
`protocolVersion` в sync. **Действие:** заморозить префикс `/api/v1/mobile`,
контракты в api-contracts версионировать директориями (`v1/`), sync-протокол
несёт `protocolVersion`, сервер отвечает 426 на устаревший.

## 4. Offline-sync недооценён планом

«Phase 6: порт mtm-offline-sync-spec» звучит как задача на неделю — это
неправда, это сложнейшая подсистема продукта. Конкретные дыры:

- Фото — большие бинарники, им нельзя жить в JSON payload outbox-операции.
  Нужен отдельный upload-канал (presigned URL + retry) и связка
  `clientPhotoId` ↔ операция.
- Порядок применения: «задача закрыта офлайн» + «фото к ней» должны
  примениться в правильном порядке при пуше пачки операций.
- **Действие:** спроектировать и прототипировать sync-протокол ДО мобильного
  UI; e2e-тест с симуляцией обрывов сети — обязателен в Definition of Done
  Phase 6.

## 5. Auth не выбран, а это блокер Phase 0

`User.passwordHash String?` — моё молчаливое «решим потом» в самом
чувствительном месте. Нерешённые вопросы: NextAuth/Lucia/custom JWT; refresh
для offline-мобильного (токен должен переживать недели без сети); как
логинится STORE_STAFF — у сотрудника аптеки часто НЕТ email (MTM решал
телефоном/кодом). Жёсткий enum UserRole без Permission-таблиц — осознанный
v0-компромисс, кастомные роли невозможны до v2. **Действие:** решить до
скаффолда web; предложение — custom JWT (access 15м + refresh 30д, ротация)
и login по employee code/телефону для полевых.

## 6. Фото-pipeline не спроектирован

S3-compatible «выбран», но не выбран провайдер и не спроектировано: путь
загрузки с мобильного (через API vs presigned — при 100 точках presigned
обязателен), thumbnails (worker-джоба), EXIF надо СОХРАНЯТЬ (требование
watermark-спеки — форензика фото), а CDN/оптимизаторы его стрипают, retention
и стоимость (фото — главный потребитель storage). **Действие:** мини-ADR до
Phase 6.

## 7. Идемпотентность импорта задекларирована, но не спроектирована

docs/04 требует «повторяемый и безопасный» импорт 1С, ImportBatch есть, но
что происходит при падении джобы на строке 50k из 100k? Upsert по natural
key снапшотов (как раз NULLS NOT DISTINCT индексы) + перезапуск батча должны
давать тот же результат. **Действие:** правило — импорт пишет только через
upsert по natural key; тест «двойной прогон = один результат».

## 8. Decimal и сериализация к мобильному

Prisma Decimal не сериализуется в JSON для React Native без потерь/сюрпризов
(Codex тоже это флагал). **Правило:** api-contracts нормализуют Decimal →
string на границе; мобильный локально считает в целых копейках/тийинах.

## 9. packages/core рискует стать свалкой

«Чистая математика в core» — правильное решение, но без границы оно
деградирует в utils-помойку с импортами Prisma. **Действие:** eslint
`no-restricted-imports` в core (запрет @prisma/*, next, react) — дешёвый
автоматический забор.

## 10. Процессные дыры Phase 0

- CI нет: docs/04 требует проверки перед merge, но ни GitHub Actions, ни
  lint-конфига, ни единого тест-раннера (я в core взял node:test+tsx ad hoc —
  переехать на vitest везде).
- prisma-client-js в pnpm-монорепо: задать явный `output` в generator, иначе
  known-грабли с резолвом клиента из workspace-пакетов.
- i18n (az/ru) всё ещё не решён — до скаффолда web выбрать next-intl и
  каталог messages; это НЕ «потом», потому что перфорирует каждый компонент.
