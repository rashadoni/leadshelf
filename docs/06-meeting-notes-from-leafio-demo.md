# Выводы из демо Leafio/Shelf

Этот файл фиксирует функциональные выводы по демонстрации, которую смотрели по Teams.

## 1. Библиотека оборудования

Система позволяет создавать собственную библиотеку оборудования:

- торговый стеллаж;
- паллета;
- холодильная витрина;
- стеллаж с перфорацией/крючками;
- шкаф с ячейками;
- тумба с ячейками;
- торговый стол;
- торговый стенд.

Ключевые параметры:

- ширина оборудования;
- высота;
- глубина;
- количество полок;
- толщина полки;
- глубина полки;
- отступы сверху/снизу;
- расстояние между полками;
- количество рядов;
- посадочные места.

Дополнительные настройки:

- auto seating / автопосадка;
- auto compression / автосжатие для мягких упаковок;
- фейсинги;
- глубина выкладки;
- размещение под углом;
- товар на товар;
- товар лежа/стоя.

Вывод: это должно быть самостоятельным core-модулем, а не частью planogram editor.

## 2. Форматы и индивидуальные планограммы

Есть два режима:

- форматная модель - одна планограмма активна на группе аптек;
- индивидуальная планограмма - действует только на конкретной аптеке.

Вывод: LeadShelf должен хранить assignments отдельно от planogram version:

- `PlanogramVersion`;
- `StoreFormat`;
- `PlanogramAssignment`.

Иначе невозможно нормально масштабировать изменения на 100 аптек.

## 3. План зала

В конструкторе плана зала есть:

- список магазинов/аптек;
- список форматов;
- canvas;
- размещение оборудования;
- копирование/использование форматных решений.

Вывод: floor plan должен быть отдельным canvas-модулем. Не надо смешивать его с planogram canvas.

## 4. Номенклатура и 1C

Из 1C/учетной системы забираются:

- дерево номенклатуры;
- название товара;
- артикул;
- штрих-код;
- габариты;
- цена;
- текущий остаток;
- продажи;
- категории;
- бренды;
- поставщики;
- дополнительные характеристики;
- ассортиментная матрица.

Обмен ежедневный ночью, чтобы утром данные были актуальны.

Вывод: нужен import pipeline + snapshots + import quality report.

## 5. Заполнение планограммы

Есть два способа:

### Ручной

Пользователь выбирает товары из номенклатуры, фильтрует и размещает на полке.

### Автоматический

Пользователь выбирает зону и задает правила:

1. Ассортимент: категория, бренды, поставщики, характеристики.
2. Сортировка: ABC, оборот, бренд, цена, KVI, поставщик, название, высота упаковки.
3. Исключения: убрать товары из выборки.
4. Auto-facing: распределить свободное место по продажам, объему продаж или прибыли.
5. Доли брендов: процент полки для каждого бренда.

Затем система загружает товары в зону.

Вывод: auto placement должен быть rule engine с объяснимым результатом.

## 6. Визуализация

В планограмме есть:

- 2D вид;
- 3D вид;
- цветовые раскраски;
- дубли товаров;
- брендовые блоки;
- раскраска по наценке;
- раскраска по остаткам/дням запаса;
- раскраска по расположению/полкам.

Вывод: color overlays нужно проектировать как отдельный layer, а не как часть базового товара.

## 7. Табличные данные

Пользователь может открыть таблицу товаров по планограмме:

- SKU;
- бренд;
- производитель;
- процент полки;
- цена закупки;
- сумма закупки;
- сумма продажи;
- текущий остаток;
- текущий запас;
- выбранные колонки;
- группировка;
- Excel export.

Вывод: таблица - не второстепенная фича. Для категорийного менеджера она так же важна, как canvas.

## 8. Мобильное приложение

Мобильное приложение показывает:

- задачи и планограммы;
- количество задач по статусам;
- список планограмм;
- планограмму на экране;
- товар при клике;
- список изменений;
- геолокацию на плане зала;
- возможность отправить фото;
- barcode scanner;
- комментарии/feedback.

Задача мобильного приложения - подтверждение факта и простое выполнение.

Вывод: mobile MVP должен быть очень простым и offline-first.

## 9. Контроль выполнения

После публикации планограммы задача уходит на торговую точку. Сотрудник делает выкладку и отправляет фото. Центральный офис видит фото как подтверждение выполнения.

Вывод: publish flow должен создавать immutable task snapshot.

## 10. Аналитика

Показаны блоки:

- ABC по обороту/себестоимости/прибыли/количеству;
- продажи по обороту/себестоимости/прибыли/количеству;
- heatmaps по планограмме;
- heatmaps по торговому залу;
- dashboard: активные планограммы, магазины с планограммами, оборот на метр, прибыль, SKU, линейный метраж;
- ассортиментные расхождения: новые активные товары без выкладки, неактивные товары на выкладке;
- like-for-like сравнение периодов;
- задачи по статусам и исполнителям;
- коэффициент отдачи: доля в продажах vs доля в выкладке;
- доля полки по брендам/группам;
- AI assistant по отчетам.

Вывод: analytics должна идти после стабильных данных и публикаций, но data model должна сразу поддерживать эти отчеты.

## 11. Главный вывод по продукту

LeadShelf должен быть не просто "редактор планограмм", а система:

```text
Оцифровать торговый зал
  -> создать планограммы
  -> опубликовать на сеть
  -> проконтролировать выполнение
  -> проанализировать эффективность
  -> улучшить выкладку
```
