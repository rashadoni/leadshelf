# Решения, согласия и несогласия

## С чем я согласен

### 1. MTM надо отделять от CRM

Согласен. В LeadDrive MTM оказался рядом с CRM, но LeadShelf - другой продукт. Если оставить его внутри CRM, продукт будет восприниматься как "еще один модуль", а не как специализированная система для мерчендайзинга.

### 2. Нужно оставить только core задачи

Согласен. Core:

- товары;
- оборудование;
- план зала;
- планограмма;
- публикация;
- мобильное исполнение;
- фото;
- аналитика.

Все остальное - вторично.

### 3. Форматы обязательны

Согласен. Для сети аптек ключевая ценность - не нарисовать одну полку, а масштабировать выкладку на десятки/сотни точек.

### 4. ERP/1C интеграция должна быть рано

Согласен. Без размеров, остатков, цен, продаж и ассортимента планограмма быстро превращается в красивый редактор без управленческой пользы.

### 5. Мобильное приложение должно быть простым

Согласен. Мобильный пользователь должен:

- увидеть задачу;
- понять, куда подойти;
- увидеть, что поставить;
- сделать фото;
- оставить комментарий.

Не надо превращать мобильное приложение в маленький web admin.

## С чем я не согласен / что не советую

### 1. Не советую начинать с 3D

3D продает идею, но не решает основную операционную боль. Начать нужно с точного 2D и таблиц. 3D подключить как viewer.

### 2. Не советую начинать с AI object detection

AI дорогой, требует данных, дает ложное ощущение готовности. Сначала нужно иметь:

- корректные планограммы;
- golden reference;
- фото-подтверждение;
- ручную проверку;
- данные по товарам.

AI должен усиливать систему, а не заменять отсутствующий процесс.

### 3. Не советую хранить активную разработку в Google Drive

Google Drive хорош для документов и архивов. Для активного кода опасен:

- конфликты файлов;
- непредсказуемая синхронизация;
- проблемы с `node_modules`;
- медленная работа;
- риск сломать git metadata.

Код: локально + GitHub. Drive: архивы и экспорт.

### 4. Не советую переносить весь код MTM

Там много полезного, но он вырос как часть LeadDrive. Если переносить все, получится та же сложность. Нужно переносить идеи и отдельные куски после ревью.

### 5. Не советую делать универсальный JSON на все

JSON удобен для быстрого старта, но опасен для отчетов. Для планограммы часть данных можно хранить JSON-ом, но ключевые сущности должны быть нормализованы:

- product;
- store;
- equipment;
- planogram version;
- placement;
- task;
- snapshot metrics.

## Главные риски

### Риск 1: редактор планограмм станет слишком сложным

Как снизить:

- начать с одного типа оборудования - стеллаж;
- manual placement first;
- capacity validation;
- потом auto placement.

### Риск 2: плохие данные из 1C

Как снизить:

- data quality dashboard;
- missing dimensions report;
- import logs;
- manual correction UI.

### Риск 3: мобильное приложение без offline провалится в магазинах

Как снизить:

- offline outbox с первого мобильного релиза;
- фото сохранять локально до успешного upload;
- idempotency keys.

### Риск 4: отчеты будут медленными

Как снизить:

- snapshot tables;
- nightly aggregation;
- indexes;
- не считать все BI на лету.

### Риск 5: AI будет обещать больше, чем может

Как снизить:

- human review;
- confidence thresholds;
- не скрывать неопределенность;
- хранить raw detections и версию модели.
